# 구름사이

지금 있는 곳의 날씨만 확인하는 대신, **도착할 시간의 예보를 비교해 활동하기 좋은 도시와 출발 시간을 찾는 서비스**입니다.

Vue.js 수업에서 처음에는 서울·수원·창원·부산의 날씨 카드를 만들었습니다. 카드를 완성한 뒤에도 사용자가 할 수 있는 일은 현재 날씨를 읽는 것뿐이었습니다. 비가 오는 날 여행, 러닝, 등산 계획을 세운다면 “여기는 비가 오는가?”보다 “이동할 수 있는 곳 중 어디가 더 나은가?”가 더 필요한 질문이라고 생각했습니다. 그래서 수업에서 만든 카드, 검색, Router, Pinia, Axios 실습을 하나의 이동 판단 흐름으로 다시 연결했습니다.

- 배포 주소: `https://agenticlab-sh.github.io/skala-vue/`
- 수업 실습 기록: 배포 화면 하단의 `수업 실습 기록` 메뉴에서 72~270쪽 코드 챌린지를 확인할 수 있습니다.

## 사용 흐름

1. 출발 도시와 출발 시각을 정합니다.
2. 러닝, 등산, 바다, 풋살, 자전거 중 하고 싶은 활동을 고릅니다.
3. 이동 가능한 도시의 **도착 예상 시각**을 계산합니다.
4. 해당 시각과 가장 가까운 예보를 골라 활동 적합도를 비교합니다.
5. 가장 나은 목적지뿐 아니라 2·3순위와 3시간, 6시간 늦게 출발했을 때의 결과도 보여 줍니다.
6. 다시 보고 싶은 도시는 관심 도시로 저장하고, 상세 화면에서 새 출발지로 이어서 계획합니다.

단순히 “맑음”인 도시를 고르지는 않았습니다. 등산과 자전거는 바람의 영향을 더 받으며, 풋살은 약한 비에도 계획이 달라질 수 있습니다. 활동마다 허용 범위를 다르게 두고 강수 45%, 기온 25%, 바람 20%, 습도 10%의 가중치로 점수를 계산했습니다. 점수와 함께 추천 이유를 표시해 결과를 다시 판단할 수 있게 했습니다.

## 실행 방법

Node.js 20.19 이상 또는 22.12 이상이 필요합니다.

```bash
npm install
npm run dev
```

코드 정리와 제출용 빌드는 다음 명령으로 확인합니다.

```bash
npm run format
npm run lint
npm run build
npm run build:staging
npm run build:production
npm run preview
```

## API 사용 방식

### OpenWeather 개인 키가 있는 로컬 환경

수업에서 사용한 OpenWeather API를 그대로 확인하려면 `.env.local` 파일을 만들고 개인 키를 작성합니다. 이 파일은 Git에 포함하지 않습니다.

```env
VITE_OPENWEATHER_API_KEY=발급받은_키
```

키가 있으면 다음 두 API를 사용합니다.

- Current Weather: 현재 날씨
- 5 day / 3 hour Forecast: 출발·도착 시간대 예보

### 공개 배포 환경

Vite의 환경 변수는 빌드 결과에 포함되므로 GitHub Pages에서 API 키를 비밀로 보관할 수 없습니다. 키를 저장소 Secret에 넣어 빌드하더라도 최종 JavaScript에서는 확인할 수 있기 때문에 사용하지 않았습니다.

공개 화면은 키가 필요 없는 Open-Meteo의 실시간 예보를 사용합니다. API 제공자가 달라도 추천 로직은 바뀌지 않도록 OpenWeather와 Open-Meteo 응답을 `temperature`, `humidity`, `windSpeed`, `precipitationProbability`, `time` 형식으로 먼저 정리했습니다.

추가로 다음 API를 사용했습니다.

- OSRM Route API: 육지 도시 사이의 도로 거리와 예상 시간
- SunriseSunset.io: 도시 상세 화면의 일출·일몰

경로 요청이 실패하면 화면을 멈추지 않고 직선거리에 도로 보정값을 더한 추정값으로 바꿉니다. 이때 결과 아래에 `직선거리 기반 추정`이라고 표시합니다. 제주는 자동차 경로로 표현하는 것이 맞지 않아 공항 이동 시간을 포함한 항공 추정으로 따로 계산합니다.

## 화면과 코드 구성

| 경로 | 역할 |
| --- | --- |
| `/` | 출발 조건 입력, 목적지 추천, 후보 비교, 출발 시간 비교 |
| `/weather/search` | 8개 도시의 현재 날씨, URL query 검색, 관심 도시 필터 |
| `/weather/:cityId` | 현재 날씨, 시간대별 예보, 일출·일몰 상세 |
| `/about` | 서비스로 발전시킨 과정, 데이터 흐름, 실제 API 키 누락 상태 |
| `/challenges` | PDF 72~270쪽 코드 챌린지와 단계별 실습 |

주요 소스의 책임은 다음과 같이 나눴습니다.

- `useTripPlanner.js`: 이동 가능 도시 선별, 날씨 요청, 경로 재확인, 추천 정렬
- `weatherApi.js`: OpenWeather·Open-Meteo·SunriseSunset 요청과 공통 형식 변환
- `routeApi.js`: OSRM 요청, 거리·시간 추정, 제주 항공 이동 분리
- `weatherScore.js`: 활동별 점수와 추천 이유 계산
- `configStore.js`: 온도 단위, 관심 도시, 마지막 검색 조건 저장
- `components/planner`: 입력, 대표 추천, 후보 목록, 출발 시간 비교 화면

기능을 늘리기 전에 `PRODUCT.md`, `DESIGN.md`, `IA.md`, `TESTING.md`에 이번 제출에서 할 일과 하지 않을 일, 화면 상태, 검증 항목을 먼저 적었습니다. 실제 코드와 맞지 않는 문서가 되지 않도록 구현 후 다시 대조했습니다.

## 과정별 배운 점

### 1. 반응형 상태와 계산 속성

처음 만든 72쪽 실습에서는 일반 변수와 `ref`를 같은 버튼으로 바꾸어 보며 화면 갱신 차이를 확인했습니다. 서비스에서는 출발지, 활동, 시간, 이동 가능 범위를 `ref`로 관리하고 선택 도시와 현재 활동 정보는 `computed`로 찾습니다.

추천 계산에 필요한 값까지 모두 템플릿 안에서 처리하려고 하니 화면 코드가 금방 길어졌습니다. API 요청과 점수 계산을 `useTripPlanner` composable로 옮긴 뒤 view는 입력값을 전달하고 상태를 보여 주는 역할만 맡겼습니다.

### 2. 컴포넌트와 데이터 전달

입력 폼, 대표 추천, 후보 도시, 시간 비교를 각각 컴포넌트로 나눴습니다. 부모는 props로 현재 값을 전달하고, 폼은 `update:` emit과 `submit` emit으로 변경 사항을 돌려줍니다. `/challenges`에는 props·emits뿐 아니라 default·named·scoped slot, provide·inject 실습도 함께 남겨 두었습니다.

처음에는 추천 카드마다 비슷한 마크업을 복사했는데, 점수 표현과 이동 시간 문구를 수정할 때 여러 곳을 고쳐야 했습니다. 대표 결과와 후보 결과의 역할은 다르므로 두 컴포넌트로 나누되, 점수 계산 자체는 `weatherScore.js` 하나만 사용하도록 정리했습니다.

### 3. Router로 사용자 흐름 만들기

메인 추천, 도시 목록, 도시 상세, 만든 과정, 코드 챌린지를 Router view로 분리했습니다. 도시 상세는 `/weather/:cityId` 동적 경로를 사용하고, 검색어는 query에 남겨 새로고침해도 같은 결과를 볼 수 있습니다. 없는 도시 코드는 전역 가드에서 확인한 뒤 404 화면으로 보냅니다.

로컬에서는 `createWebHistory()`가 잘 동작했지만 GitHub Pages는 하위 경로를 서버에서 다시 찾을 수 없어 새로고침 시 404가 날 수 있었습니다. 별도 서버 설정 없이도 동적 경로를 유지하기 위해 최종 배포에서는 `createWebHashHistory()`로 변경했습니다.

### 4. Pinia로 화면 사이의 선택 유지하기

온도 단위, 관심 도시, 마지막 검색 조건은 한 화면에만 두면 상세 화면으로 이동할 때 사라집니다. `configStore`로 옮기고 `localStorage`에 저장해 다시 접속해도 유지되도록 했습니다. 저장된 JSON이 깨져도 앱 진입이 막히지 않도록 읽는 부분에는 기본값 처리를 넣었습니다.

수업의 Pinia 실습에서 Store state와 getter를 구조 분해할 때 `storeToRefs()`가 필요한 이유를 확인했습니다. 해당 실습은 `/challenges`에 남기고, 실제 서비스에서는 Store 자체의 반응형 속성을 사용했습니다.

### 5. Axios와 서로 다른 API 응답 정리하기

OpenWeather의 5일 예보는 3시간 간격이고 Open-Meteo는 1시간 간격이라 그대로 사용하면 추천 코드가 API마다 달라집니다. 요청 직후 두 응답을 같은 객체로 바꾸고, 도착 시각과 시간 차이가 가장 작은 예보를 찾았습니다. API 요청은 도시마다 동시에 보내되 `Promise.allSettled()`를 사용해 한 도시가 실패해도 확인된 도시로 계속 비교합니다.

같은 도시를 화면 이동 때마다 다시 요청하지 않도록 10분 캐시를 두었습니다. 상세 화면에서 새 값이 필요한 경우에는 `force` 옵션으로 캐시를 건너뜁니다.

### 6. Element Plus와 실패 상태

수업에서 다룬 Element Plus는 도시 날씨 화면과 코드 챌린지에 사용했습니다. 메인 서비스는 모든 요소를 라이브러리 카드로 만들기보다 입력과 결과의 위계가 보이도록 기본 HTML과 CSS를 함께 사용했습니다. 전체 라이브러리를 한꺼번에 등록하지 않고 실제로 쓴 컴포넌트만 등록했습니다.

OpenWeather 키가 없던 첫 화면에서는 요청 버튼만 비활성화했습니다. 이유는 알 수 있었지만 서비스 전체는 사용할 수 없었습니다. 최종 화면에서는 키가 없는 상태를 감지해 공개용 실시간 예보로 전환합니다. `/about`에서 현재 실행 환경이 어느 제공자를 사용하는지 직접 확인할 수 있습니다.

![초기 OpenWeather 키 누락 화면](docs/weather-api-key-missing.jpg)

### 7. 코드 품질과 배포

ESLint, Oxlint, Prettier를 실행하고 일반·staging·production 세 모드로 빌드했습니다. 이전에 의존성을 수동으로 나누는 설정을 추가했을 때 preview 화면에서 `q is not a function` 오류와 빈 화면이 발생했습니다. 정확한 내부 원인을 단정하지 않고 수동 분할을 제거했습니다. 대신 Element Plus에서 사용한 컴포넌트만 등록해 주 JavaScript 파일을 약 942kB에서 325kB로 줄였고, 세 빌드와 preview를 다시 확인했습니다.

GitHub Pages는 `.github/workflows/deploy-pages.yml`에서 Node 22로 production 빌드한 `dist` 폴더만 배포합니다. 공개 빌드에는 API 키를 넣지 않습니다.

## 트러블 슈팅 기록

### 실제 경로를 확인한 뒤 제한 시간을 넘긴 도시가 남았습니다

처음에는 직선거리 기반 예상 시간으로 후보를 고른 뒤 상위 네 곳만 OSRM으로 다시 확인했습니다. 6시간으로 검색했을 때 제주가 실제 경로 결과에서 6시간 33분이 되었는데도 `20%까지 허용`하던 임시 조건 때문에 화면에 남았습니다.

최종 정렬 전에 실제 경로 시간이 사용자가 정한 범위 이하인지 다시 검사하도록 수정했습니다. 제주처럼 이동 방식 자체가 다른 지역은 자동차 경로 대신 항공 이동 추정으로 분리했습니다.

### 추천 문장의 조사가 어색했습니다

도시 이름 뒤에 항상 `로`를 붙여 `대전로`, `부산로`라고 표시되었습니다. 마지막 글자의 받침을 확인하고, 받침이 없거나 ㄹ 받침이면 `로`, 그 외에는 `으로`를 붙이는 계산 속성을 추가했습니다.

### 경로 API가 실패하면 추천 전체가 사라졌습니다

날씨 결과까지 받은 뒤 경로 서버 하나가 실패하면 결과를 버리는 방식은 좋지 않았습니다. `requestDrivingRoute()` 안에서 오류를 처리하고 직선거리 기반 추정값을 반환하도록 바꿨습니다. 추천은 계속 보여 주되, 사용자가 실제 경로와 추정 경로를 구분할 수 있도록 출처를 함께 표시했습니다.

### 빠르게 조건을 바꾸면 이전 결과가 나중에 나타날 수 있었습니다

조건을 바꿔 연속으로 비교하면 먼저 시작한 요청이 늦게 끝나 새 조건의 결과를 덮을 수 있었습니다. composable 안에 요청 번호를 두고, 가장 최근에 시작한 요청만 추천 목록을 바꾸도록 했습니다. 또한 예상 이동 시간으로 통과했지만 실제 경로 확인 뒤 후보가 하나도 남지 않는 경우를 오류와 다른 빈 결과 상태로 분리했습니다.

### 온도 단위가 화면마다 다르게 적용되었습니다

도시 목록과 상세에서는 ℉로 바뀌었지만 메인 추천과 시간 비교는 계속 ℃로 표시되었습니다. 변환 함수를 `temperature.js`로 분리하고 세 화면이 같은 함수를 사용하도록 바꿨습니다. 상세 화면의 `이 도시로 다시 계획하기`도 처음에는 홈으로만 이동했는데, Pinia의 출발 도시를 먼저 저장한 뒤 이동하도록 수정했습니다.

### 공개 배포에 API 키를 넣을 수 없었습니다

처음에는 GitHub Actions Secret을 사용하면 안전하다고 생각했습니다. 하지만 Vite는 브라우저에서 사용할 값을 빌드 파일에 넣기 때문에 Secret으로 전달해도 결과물에서 키를 찾을 수 있습니다. 서버를 새로 만드는 것은 이번 Vue 과제 범위를 넘어간다고 판단했습니다.

로컬에서는 수업에서 배운 OpenWeather 현재·예보 API를 사용하고, 공개 화면은 키 없는 Open-Meteo 예보를 사용하는 방식으로 나눴습니다. 제공자가 다르다는 사실은 README와 `/about`에 표시했습니다.

### 보조 API가 실패한 뒤에도 계속 확인 중으로 보였습니다

도시 상세에서는 날씨와 일출·일몰을 동시에 요청합니다. 일출 API만 실패해도 날씨 화면은 열렸지만, 값이 없다는 이유로 계속 `확인 중`이라고 표시되어 실제 상태와 달랐습니다. 일출 요청 상태를 따로 두어 성공하면 시간을, 실패하면 `별도 API 확인 실패`를 보여 주도록 바꿨습니다.

### XSS 주의 실습이 위험한 코드를 그대로 실행하고 있었습니다

`v-html`의 위험을 설명하면서 입력한 문자열을 다시 `v-html`로 출력하고 있어 설명과 동작이 맞지 않았습니다. HTML 적용 비교는 코드에 작성한 고정 문자열로만 남기고, 사용자가 입력한 값은 보간법으로 출력하도록 수정했습니다. 태그를 입력해도 화면에서는 문자 그대로 보입니다.

### 강수량 유무를 강수확률처럼 표시했습니다

현재 비가 오면 70%, 오지 않으면 0%로 바꿔 표시했는데, 현재 강수량과 강수확률은 같은 값이 아닙니다. 현재 시각과 가장 가까운 예보의 강수확률을 사용하도록 고쳤고, 값을 구하지 못한 도시는 임의의 숫자나 정적 기온 대신 `–`로 표시했습니다.

## 최종 확인

- 서울 출발·러닝, 창원 출발·바다 조건에서 실제 추천 결과가 바뀌는 것을 확인했습니다.
- 추천 목적지의 도착 시각, 강수확률, 점수, 이동 시간이 함께 바뀌는 것을 확인했습니다.
- 후보 도시를 선택해 동적 상세 경로로 이동하는 것을 확인했습니다.
- 도시 검색어 `창원`이 URL query에 남고 한 도시만 표시되는 것을 확인했습니다.
- ℃에서 ℉로 바꾼 뒤 상세와 목록 화면이 함께 갱신되는 것을 확인했습니다.
- 메인 추천과 출발 시간 비교의 기온도 같은 단위로 갱신되는 것을 확인했습니다.
- 창원을 관심 도시로 저장하고 필터를 켰을 때 URL query와 목록이 함께 바뀌는 것을 확인했습니다.
- 창원 상세에서 다시 계획하기를 누르면 홈의 출발 도시가 창원으로 바뀌는 것을 확인했습니다.
- 직접 비교한 뒤 결과 제목으로 키보드 포커스가 이동하는 것을 확인했습니다.
- 없는 도시 코드가 404 화면으로 이동하는 것을 확인했습니다.
- 상세 화면에서 일출·일몰 보조 API 실패가 `확인 중`으로 남지 않는 것을 확인했습니다.
- XSS 주의 실습의 사용자 입력이 HTML로 실행되지 않는 것을 확인했습니다.
- 도시 날씨 API 실패 행이 정적 기온을 실시간 값처럼 표시하지 않는 것을 확인했습니다.
- `/challenges`의 13개 코드 챌린지 구역이 유지되는 것을 확인했습니다.
- 320px, 390px, 768px, 1440px 화면에서 가로 넘침이 없는 것을 확인했습니다.
- 브라우저 console error와 warning이 없는 것을 확인했습니다.
- format, lint, 일반·staging·production build를 통과했습니다.

예보와 이동 시간은 실제 계획을 돕는 참고 정보입니다. 특히 항공 이동 시간과 API 실패 시의 거리는 추정값이며, 화면에 해당 출처를 표시합니다.
